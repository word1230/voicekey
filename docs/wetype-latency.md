# 微信渠道的停等延迟

结论：微信渠道慢，是 `crates/core/src/wetype.rs` 的**停等**写法造成的，不是微信服务端算得慢。说满 20 秒左右就会整段丢失（应用层的 15 秒超时兜底）。修法与验收判据见最后一节。

## 机制

`wetype.rs` 是唯一一个发一批就阻塞等回复的引擎（`wetype.rs:59`，注释写的"一条 WSS 上严格一问一答"）。于是每个周期的墙钟时间是

```
周期 = 批次音频时长 D + 往返 RTT
吃进速率 = D / (D + RTT)   —— 恒小于 1
```

**只要等回复，吞吐就永远追不上实时**，而录音帧流是无界通道（`audio.rs:231`），欠账没有上限：每说 1 秒欠 `RTT/D` 秒，随说话时长线性增长。

其它引擎都是流水线（发出去不阻塞等回复），这是它们不受影响的原因：豆包收发分离（`doubao.rs:227` + 接收任务）、千问 `tokio::select!` 同时收发（`qwen.rs:80`）、讯飞 1ms 超时顺手收（`ifly.rs:140`）、百度上行/下行两个 task。搜狗虽然也等回复，但批次大得多（10 包 = 200 ms，`sogou.rs:9`），实测跟得上。

## 实测

同一段 38.4 秒语音（`ios/Resources/sample.wav` 重复 8 遍），实时节奏喂入，同机同网络：

| 场景 | 总耗时 | 说完后还要等 |
|---|---|---|
| 豆包（流水线） | 41.3 s | ≈ 2.9 s |
| 搜狗（停等，200 ms 一批） | 42.2 s | ≈ 3.8 s |
| 微信（停等，6 包 = 120 ms） | 62.0 s | ≈ 23.4 s |
| 微信（停等，24 包 = 480 ms） | 48.1 s | ≈ 9.5 s |
| 两条微信流同时跑 | 46.0 / 47.2 s | 互不拖慢 |

反推出 RTT：6 包时每周期 0.189 s（322 个请求）→ RTT ≈ 69 ms；24 包时 0.581 s（81 个请求）→ RTT ≈ 101 ms。即服务端处理 120 ms 音频只要 ~70 ms，**比实时快**；慢的是客户端在等它。

两条流并行不互相拖慢，说明服务端能并行处理多条流——这是方案 A/B 可行的依据。

## 为什么"说久了会出错"

不是识别错，是整段被超时丢掉。`controller.rs:728` 在松手（`end()`）后起 15 秒定时器，到点 `abort("识别超时")`，而 `abort → cancel()` 会 `gen += 1`，之后到达的 `Msg::Done` 因 gen 不匹配被忽略（`controller.rs:247`）——结果被丢弃、什么都不上屏。

按上面的欠账速率推算：说话 10 s → 松手后还要 5.8 s（没事）；说话 25 s → 14.5 s 加上定稿整理，直接撞上 15 s 红线。**所以这个渠道一口气能说的上限约 20 秒。**

注意：vk-test 没有这个 15 秒超时，上面"说完后还要等 23.4 s"是 vk-test 一路等到底测出来的；"应用层会在 15 s 处掐掉"是从代码推出来的。**真机上已确认会触发**（说久了会看到"识别超时"、结果整段丢失）。

## 复现

```bash
# 38.4 s 测试音频：sample.wav 重复 8 遍，每遍之间垫 200ms 静音
python3 - <<'EOF'
import wave
src = wave.open("ios/Resources/sample.wav"); d = src.readframes(src.getnframes())
out = wave.open("/tmp/bench.wav", "wb"); out.setparams(src.getparams())
for _ in range(8):
    out.writeframes(d); out.writeframes(b"\x00\x00" * 3200)
EOF

cargo build --release -p voicekey-core --bin vk-test
/tmp/ts.sh /path/to/target/release/vk-test wetype /tmp/bench.wav   # ts.sh 见下
```

`vk-test` 用 `file_frames(wav, true)` 按实时喂帧（`audio.rs:361`），而引擎内的 `lead()` 又把消费速率钉在 20ms/帧（`audio.rs:78`）。**所以"总耗时 > 音频时长"就等于引擎处理不过来**，超出的部分就是欠账。读这些数字时别把它当成网络或编码的开销。

`ts.sh`（给每行输出打上相对时间戳，用来观察实时文字落后的过程）：

```bash
#!/usr/bin/env python3
import sys, time
t0 = time.time()
for line in sys.stdin:
    print("%7.2f  %s" % (time.time() - t0, line.rstrip()), flush=True)
```

## 修

按顺序做，每步都有判据。

### 1. 先验证流水线（方案 A）

把上行和收回复拆开：加一个接收任务持续 `ws::recv` 并更新文字，发送侧只 `send`、不等回复（照 `doubao.rs` 的样子改）。回复是累计全文（服务端每次都回整段），所以接收侧直接取最新一条即可，不需要按 task_id 配对。取消掉重连重发逻辑时留意：流水线后已经发出去的批次没法重发。

判据：`vk-test wetype /tmp/bench.wav` 总耗时 **≤ 43 s**（豆包 41.3 / 搜狗 42.2 是参照）。达到就是根治。

风险：那个"严格一问一答"的注释说明作者可能踩过坑，服务端也许只认交替请求。所以先做原型验证，别直接替换。

**结论：已验证，达标。** 同一段 38.4 s 音频，流水线 **40.7 s**（两次复测 40.74 / 40.75 s，稳定）、旧的停等 **67.9 s**（两条路径定稿文字完全一致）。说明服务端**接受并发/流水线请求**，不强制交替，"严格一问一答"的顾虑不成立。

原型已实现且为默认路径：`wetype.rs` 里发送侧是 `Sender`（只 `send`）、接收侧是 `receive` 任务（持续收、解出累计全文写进共享态）。`WETYPE_STOPWAIT=1` 可退回旧的停等实现做 A/B。代价：流水线跑完不再把连接放回 `self.client`（收发两半拆开后无法重组），每次录音都要重新握手 ~400 ms；预热仍能让首次录音省掉这段。真要长期留用，再考虑把复用改造成保留发送半 + 接收任务句柄。


### 2. 服务端不认并发就换多连接（方案 B）

开 2 条 WSS，把批次轮流发到两条上，每条内部仍然一问一答。等效吞吐 `2 × D/(D+RTT)` ≈ 1.26×，够用。判据同第 1 步。双流并发已经在两个不同设备身份下验证过没问题，同 uin 多连接还没验。

### 3. 顺手改掉 15 秒硬超时

`controller.rs:728` 的 15 秒应该随录音时长伸缩（改成 `15 + 录音秒数 × 0.6` 之类），否则任何渠道只要欠账超过 15 秒就同样丢结果。

判据：真机说 30 秒以上，HUD 不出现"识别超时"，且出字完整。

**已改**：`controller.rs` 新增 `record_started`，`end()` 里超时改为 `15 + 录音秒数 × 0.6`。方案 A 落地后微信渠道本身不再欠账，这条只是给任何残余欠账兜底。

### 应急（一行，治标）

`wetype.rs:16` 的 `PACKETS_PER_REQUEST` 6 → 24：可用时长从 ~20 s 提到 ~35 s，代价是实时文字从 120 ms 一跳变成 480 ms 一跳。只在 1 和 2 落地前用。

## 边界

- **没法用这段音频判准确率。** 它是同一句话重复 8 遍，各引擎的定稿都会被重复内容带偏（豆包只留一句、搜狗截断）。要查"识别错了"必须用不重复的长句录一遍。
- 松手后还有一段定稿整理轮询（`wetype.rs:123`，最多 8 × 250 ms，实测首轮即回）。
- 握手约 400 ms（`wetype.rs:36`），有 prewarm 时会复用连接，不算在欠账里。
